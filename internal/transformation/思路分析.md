# Refashion 动态幻化 — 思路分析

> 本文梳理 `internal/transformation` 动态幻化的**底层原理与实现思路**：
> 从那串特征字节定位函数开始，到装 hook、捕获装备指针、最终改写幻化ID 的完整链路。
> 对应代码：`refashion_core.go`（核心）、`transformation.go`（流程编排）、`wininput.go`（窗口/输入）。

---

## 一、核心概念分层（必须先分清的事）

### 1. 函数入口地址 vs 物品数据地址

| 概念 | 是什么 | 谁拥有 | 是否 ASLR 相关 |
|---|---|---|---|
| **编辑函数入口**（`hookSite`） | 一段机器指令（装备编辑器）的入口 | **游戏代码段（.text）** | 相对模块固定偏移（如 `nioh2.exe+0x1022540`），绝对地址每次启动变 |
| **物品数据地址**（`item.Addr`） | 一件装备/道具对象在内存里的位置 | 运行时由游戏在堆区分配 | 每次都不一样，动态堆地址 |

- 函数是"代码"，物品是"数据"。
- AOB 特征定位的是**函数（代码）**的位置；装备地址要靠 hook 在**运行时**捕获。

### 2. 虚拟地址 vs 物理地址

- 我们拿到的 `addr`（`rcx`/`slot` 里的值）= **用户态虚拟地址**（游戏进程地址空间视角）。
- **不是**内存条上的真物理地址；中间由 OS 页表翻译，我们不需要接触。
- 改动写入走 `WriteProcessMemory(游戏进程, addr+0x02, ...)` —— 全程使用虚拟地址。

### 3. 我们改的是"内存里的值"，不是寄存器

- `rcx` 寄存器里临时存的是装备地址，但我们**不读寄存器**。
- 钩子做的事：游戏 CPU 执行 `mov [slot], rcx`，把 rcx 的值**落进一块固定内存槽 slot**。
- 我们跨进程 `ReadUint64(slot)` 读内存得到地址。寄存器只在游戏内活，我们只碰它落下来的内存。

## 二、总体流程（一次完整的幻化）

```
① 特征定位（AOB）      → 拿到装备编辑器函数入口地址 hookSite（代码）
② 安装 hook 注入       → 函数入口被覆盖成 jmp cave，cave 里写好我们的指令
③ 捕获钩子            → 玩家选中装备时游戏执行到入口 → jmp→cave → mov [slot],rcx
④ 跨进程读取          → 外部 ReadUint64(slot) 拿到装备真实地址
⑤ 改写值            → WriteProcessMemory(addr + 0x02, 新幻化ID) + 回读校验
```

## 三、定位：AOB 特征字节（LocateHookSite）

### 那串字节是什么

CT 表给出的装备编辑器函数入口特征：

```
边界:   C3 CC CC CC CC            ← 上一函数 ret + 对齐填充（确认是"函数入口"）
入口7B: 48 83 EC 28 0F B7 11      ← sub rsp,28; movzx edx,[rcx]
函数体:  48 8B 05 ?? / 48 8B 48 20 / 48 8B 89 28 04 00 00
```

比喻：模块像一栋楼，字节特征像某间办公室门口的"门板花纹"。因为 ASLR（每次启动模块随机基址），不能直接记绝对门牌号，只能记"门板花纹"（机器码字节），然后整栋楼搜索，谁能对上就是入口。

### LocateHookSite 步骤

```go
func (r *Refashion) LocateHookSite() (uintptr, uintptr, error)
```

1. `getModuleBase` → 拿 `nioh2.exe` 模块基址 `base` + 大小（限定扫描范围）。
2. `aobScanAll(base, base+size, hookPattern(7字节))` → 搜到若干个候选点（可能撞车）。
3. 对每个候选 `h` 做 `verifyHookSite` 双重校验：
   - `h-5` 起 5 字节 == `C3 CC CC CC CC`（函数边界，排除函数内部命中）；
   - `h+7` 起匹配函数体特征（跳过 disp32）。
4. 再用 CT 12 字节模式（`ctPattern = C3..C3 48 83 EC 28 0F B7 11`）复核 `c+5 == h`（12字节起点+5=7字节起点）。
5. 返回 `(h, base)`，`h` 即装备编辑器函数入口**绝对地址**。

**注意**：这个方法**只定位不改任何内存**，纯只读。

## 2. 注入 2 部：装钩子（InstallHookAt）

### 核心动作：把函数入口覆盖成一个跳转

```go
patch[0] = 0xE9                       // jmp 相对跳转
relHook  = cave - hookSite - 5      // 相对距离（相对 hookSite+5 到 cave）
patch[1:5] = relHook                // 4 字节相对偏移
patch[5:7] = 0x90 0x90              // nop 补位，共 7 字节等长覆盖
p.write(hookSite, patch)            // ← 这就是"设钩"的实体动作
```

为什么用相对偏移：`.text` 代码地址受 ASLR 影响，绝对地址不稳定；相对距离稳定。

### 注入的几步（InstallHookAt）

1. **校验原始字节**：`hookSite` 前 7 字节必须仍是 `48 83 EC 28 0F B7 11`（防止重复注入/版本不符）。
2. **分配 cave**：`virtAllocExNear` 在 `hookSite` **±2GB** 内分配 RWX 内存（`E9` 相对跳转寻址极限）。
3. **写入 cave 代码**（`buildHookCode`）：
   ```
   cave+0x00: mov [slot], rcx     ← 钩子核心：把选装备地址写进槽
   cave+0x07: sub rsp, 28          ← 重放被覆盖的原指令
   cave+0x0B: movzx edx, [rcx]     ← 重放原指令
   cave+0x0E: jmp returnAddr       ← 跳回函数继续执行
   ```
   `slot = cave + 0x20`。
4. **patch hookSite** = `jmp cave; nop; nop`（上面）写入。
5. **刷新指令缓存** `FlushInstructionCache`。

### 注入完成后的执行流

```
游戏CPU 跑到函数入口
        │ 遇到 E9 jmp
        ▼
   cave: mov [slot], rcx   ← 我们的自定义指令真执行（写槽）
        ▼
   cave: 重放 sub rsp,28 / movzx edx...  （原指令功能不受影响）
        ▼
   jmp returnAddr（回函数继续）
```

**"游戏继续自己的机能不受影响"的关键**：被覆盖的 7 字节在 cave 里重放原样再跳回。

---

## 重要：我们怎么"拿到寄存器里的值"

- **我们不能直接读游戏线程的寄存器**（跨进程）。
- 机制是：游戏的指令 `mov [slot], rcx` 由**游戏自己的 CPU**执行，把 rcx 当前值写到**规定的内存槽 slot** 里。
- 我们再用 `ReadUint64(slot)` 从**内存**读出来。
- 也就是说：**寄存器 →(游戏写)→ 游戏内存 slot →(我们读)→ 拿到装备地址**。

## 部分：外层轮询捕获 + 改写

### traverseCapture（transformation.go）

```
每轮:
  甩鼠标到空白 → clearSlot()（写 0 清槽） → 带到前台 → 定位目标槽 → 悬停
  traverseCapture(prevAddr, 2s):
       轮询 ReadUint64(slot):
           addr != 0 且 addr != prev  → 读 ReadItem(addr) → 返回 item（捕获成功）
           否则继续轮询（120ms 间隔）
       超时 → 返回 (nil, false) → 判定"空槽/无装备" → 跳过该槽（notify前端）
```

- `clearSlot()`：每次霍动之前把槽写 0，消除上次残留陈旧指针（修复过"头部为空导致已装备的上衣被误跳"）。
- 空槽逻辑：槽保持 0 → 超时 = 无新捕获，跳过 + 上报。

### SetRefashionID（改写值）

```go
buf := []byte{byte(newID), byte(newID>>8)}
h.proc.write(item.Addr + 0x02, buf)   // 在虚拟地址 + 2 处写 2 字节
// 回读校验
after := read uint16(item.Addr + 0x02)
if after != newID → error
```

- 偏移 `+0` = 物品ID，`+2` = 幻化ID，`+4` = 数量（CT 表确认）。
- **我们改的是"内存里的值"，不是寄存器。钩子给的是"地址"，我们再用地址去写内存。**

## 清理 / 还原（关于"关闭后"的问题）

| 情况 | 行为 | 结果 |
|---|---|---|
| 正常流程结束 | `defer unhook()` → `Uninstall()`：写回原始7字节 + 释放 cave | 游戏恢复原样，完全无痕 |
| 异常强杀管理器 | hook 字节残留在游戏内存；cave 未释放 | 游戏仍走 jmp → cave（重放原指令+跳回）→ 游戏行为正常；但 AOF 找不到原始字节，下次注入需先 `cleanup` |
| 游戏重启 | 进程/内存全部释放，模块重新加载 | 全部还原，无副作用 |

`UninstallLeftover`/`CleanupLeftover` 用于强杀残留的场景（基址+固定偏移 hard code 还原）。
